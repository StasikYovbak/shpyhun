# ЕХО · НЕОНОВИЙ КУР'ЄР

Піксельний кіберпанк-платформер для Android: 10 секторів, 5 босів,
11 зброй, процедурна графіка й музика. Уся графіка й увесь звук
**згенеровані кодом** — у репозиторії немає жодного завантаженого
звідкись спрайта чи семпла.

**Стек:** Vite + PixiJS 8 (WebGL) + Capacitor 7 → справжній APK з
повноекранним immersive-режимом. Фізика — фіксований крок 1/60 с,
AABB-колізії, окремий шар світла й власний GLSL-шейдер палітри.

**Статус: `v0.9-playable`** — гра проходиться від початку до кінця.
Що працює: усі 10 рівнів (валідатор прохідності зелений), 5 босів із
фазами, арсенал з 11 зброй із видачею за сектори, секретна Ехо-Призма з
трьох фрагментів, саундтрек на Tone.js із чотирма адаптивними шарами,
налаштування керування, система катсцен із демо-сценою, окрема
анімація атаки під кожну зброю, власна механіка на кожному секторі,
навчання з дев'яти кроків, тренувальна кімната з чотирьох зон, редактор
розкладки керування й три режими складності.
32 набори автотестів у справжньому Chromium — усі зелені.
Є режим розробника (`DEV_MODE`) з панеллю читів і діагностики —
у релізній збірці вирізається повністю.

## Повний екран: що саме зроблено

Причина «маленького екрана» — адресний рядок браузера. В APK його немає, а
системні панелі прибираються так:

| Шар | Що зроблено |
|---|---|
| Capacitor | `StatusBar.setOverlaysWebView(true)` + `StatusBar.hide()` при старті |
| Android | `SYSTEM_UI_FLAG_IMMERSIVE_STICKY \| FULLSCREEN \| HIDE_NAVIGATION \| LAYOUT_STABLE` у `MainActivity`, **перевстановлюються в `onWindowFocusChanged`** — інакше навігаційна панель повертається після згортання |
| Тема | `android:windowFullscreen`, прозорі status/navigation bar, `windowLayoutInDisplayCutoutMode=shortEdges` |
| Маніфест | `screenOrientation="sensorLandscape"`, `resizeableActivity=false`, дозволи `VIBRATE` і `WAKE_LOCK` |
| Екран не гасне | `FLAG_KEEP_SCREEN_ON` |
| Виріз камери | `viewport-fit=cover` + `env(safe-area-inset-*)`: керування зсувається, щоб кнопки не ховалися під «чубчиком» |
| Орієнтація | `ScreenOrientation.lock({orientation:'landscape'})` |
| Кнопка «Назад» | перехоплюється: у бою — пауза, у меню — крок назад, і лише з головного меню — вихід |

**Масштаб.** Внутрішній кадр лишається 480×270, але виводиться на повну
фізичну роздільність: масштаб — ціле число в **фізичних** пікселях
(`devicePixelRatio` враховано), `scaleMode = NEAREST`, тож пікселі чіткі й не
«дрижать». На витягнутих екранах замість чорних смуг з боків кадр
**розширюється по горизонталі до 528 px** — гравець бачить більше, картинка не
розтягується. Перевірено на 16:9, 19,5:9 і 20:9:

Виміряно `tests/screens.mjs` (реальні числа, не оцінка):

| Екран | Кадр | Масштаб | Зайнято X | Зайнято Y |
|---|---|---|---|---|
| 1920×1080, dpr 2 (16:9) | 480×270 | ×4 | 100 % | 100 % |
| 2340×1080, dpr 3 (19,5:9) | 528×270 | ×4 | 90 % | 100 % |
| 2400×1080, dpr 3 (20:9) | 528×270 | ×4 | 88 % | 100 % |
| 2000×1200, dpr 2 (планшет) | 500×270 | ×4 | 100 % | 90 % |
| 2712×1220, dpr 2,75 (21:9) | 528×270 | ×4 | 78 % | 88 % |
| 1280×720, dpr 1 (вікно браузера) | 528×270 | ×2 | 83 % | 75 % |

Останній рядок — плата за **цілий** масштаб: 720/270 = 2,67, тож коефіцієнт
округлюється до ×2. На телефонах, де dpr зазвичай 2,5–3, коефіцієнт виходить
×4 і екран заповнено на 88–100 %. Дробовий масштаб заповнив би все, але
пікселі почали б «дрижати» — цим не жертвуємо.

## Графіка: було → стало

| | Було (1.x, Canvas2D) | Стало (2.0, PixiJS/WebGL) |
|---|---|---|
| Малювання | ~700 викликів `fillRect` щокадру | ~650 спрайтів з **одного атласу** 512×512, батчинг в один draw-call |
| Ассети | нічого, усе малювалося наживо | `assets/atlas.png` (50 КБ, 113 кадрів) — пече `gen-assets.mjs` |
| Світло | не було | окремий additive-шар: вивіски, клинок, кулі, очі ворогів, вибухи; світло **фарбує** сусідні тайли |
| Bloom | не було | `AdvancedBloomFilter` із **порогом яскравості 0.62** — світиться лише неон, а не весь кадр |
| Мокрий асфальт | не було | дзеркальні копії джерел світла й героя нижче лінії підлоги, розмиття + прозорість 32 % |
| Спека / пар | не було | `DisplacementFilter` із процедурною шумовою текстурою над трубами та вибухами |
| Хром. аберація | не було | `RGBSplitFilter`: 0,4 px постійно, сплеск до 3 px на шкоді й на арені Гліч-Ядра |
| CRT | не було | `CRTFilter` (scanlines + кривизна + віньєтка), **за замовчуванням вимкнено** |
| Палітра | фіксовані кольори | власний GLSL-шейдер: тіні тягне в колір локації, плавний перехід між рівнями |
| Темрява метро | вирізана «дірка» на другому canvas | текстура-маска + additive-світло крізь неї |
| Дрібниці | — | тінь-пляма під героєм, підсвітка контуру кольором найближчого джерела, шарф реагує на швидкість, спалах екрана на смерть боса |

**Бюджет кадру** (Chromium, кадр 528×270, вимірює `tests/perf.mjs`):

| Сцена | Крок логіки | Побудова кадру | Спрайтів |
|---|---|---|---|
| Сектор 1 | 0,047 мс | 0,457 мс | 642 |
| Сектор 4 (бос) | 0,056 мс | 0,553 мс | 705 |
| Сектор 8 (бос) | 0,040 мс | 0,494 мс | 678 |
| Сектор 10 (бос) | 0,041 мс | 0,460 мс | 677 |

Для порівняння: у версії 1.x безпосереднє малювання коштувало ~1,0 мс
процесорного часу на кадр. Тепер процесор витрачає вдвічі менше, а розтеризація
пішла на GPU. З бюджету 16,6 мс на кадр зайнято ~0,5 мс CPU.

**Режими графіки** (Налаштування → Графіка): *Продуктивність* (без bloom,
відображень і світла), *Збалансовано* (bloom + світло + відображення),
*Максимум* (+ хроматична аберація, вища якість bloom), *Авто* — стежить за FPS
і сам знімає ефекти згори вниз, якщо просідає нижче 50, і повертає їх, коли
стабільно вище 58.

## Як отримати APK у руки

**Варіант 1 — уже зібраний.** У корені є `neon-echo-debug.apk`: скинь на
телефон, відкрий, дозволь встановлення з невідомих джерел.

**Варіант 2 — GitHub Actions (без Android Studio).**

1. Створи репозиторій на GitHub: **New repository** → назва будь-яка →
   **Create repository**.
2. Завантаж файли: на сторінці репозиторію **Add file → Upload files**,
   перетягни весь вміст цієї теки (або розпакований zip), унизу
   **Commit changes**.
3. Відкрий вкладку **Actions**. Якщо GitHub спитає — натисни
   **I understand my workflows, go ahead and enable them**.
4. Ліворуч вибери workflow **«Збірка APK»** → праворуч кнопка
   **Run workflow** → ще раз **Run workflow**.
5. Чекай ~6–8 хвилин, поки біля запуску не з'явиться зелена галочка.
6. APK можна забрати двома шляхами:
   * внизу сторінки запуску, блок **Artifacts** → `neon-echo-apk` (zip);
   * або у вкладці **Releases** — там лежить `neon-echo-debug.apk` окремим
     файлом, і це посилання можна відкрити **прямо з телефона**.
7. На телефоні: відкрий завантажений APK → Android запитає дозвіл →
   **Налаштування → Дозволити з цього джерела** → **Встановити**.
   (Шлях може називатися «Встановлення невідомих застосунків».)

**Підпис release-версії.** Створи ключ:

```bash
keytool -genkeypair -v -keystore neon-echo.keystore -alias neonecho \
        -keyalg RSA -keysize 2048 -validity 10000
base64 -w0 neon-echo.keystore > keystore.b64      # Linux
# certutil -encode neon-echo.keystore keystore.b64   # Windows
```

У репозиторії: **Settings → Secrets and variables → Actions → New repository
secret** і додай чотири секрети:
`KEYSTORE_BASE64` (вміст `keystore.b64`), `KEY_ALIAS` (`neonecho`),
`KEY_PASSWORD`, `STORE_PASSWORD`. Після цього кожна збірка
підписуватиме `neon-echo-release.apk` автоматично. Без секретів release
збереться непідписаним — на телефон ставиться debug-версія.

**Варіант 3 — локально.** Потрібні Node 20+, JDK 17, Android SDK 35:

```bash
npm ci
npm run apk:debug     # -> android/app/build/outputs/apk/debug/app-debug.apk
npm run apk:release   # -> android/app/build/outputs/apk/release/app-release.apk
adb install -r android/app/build/outputs/apk/debug/app-debug.apk
```

# Версія 3: керування, слоти зброї, арсенал, розумніші вороги

Ігрова база, сюжет, керування хрестовиною й фізика стрибка з попередніх
кроків не змінювались. Нижче — чотири звіти, яких вимагав промт, усі
числа зняті автотестами (`npm test`), а не оцінені на око.

## 1. Налаштування керування

Окремий екран **Налаштування → Керування** з живим прев'ю: шар керування
підіймається над панеллю, тож кожен рух повзунка видно одразу на самій
хрестовині й кнопках. Шар ловить дотик лише на самих блоках, тому
повзунки під ним лишаються натискними.

| Що | Діапазон | Окремо для |
|---|---|---|
| Прозорість | 20–100%, крок 5% | хрестовини й кнопок |
| Розмір | 70–160%, крок 5% | хрестовини й кнопок |
| Позиція | перетягування пальцем, прилипання до сітки 8 px | хрестовини й блоку кнопок |
| Пресети | Класика / Великі / Компакт / Ліворукий | — |
| Дзеркалення | стрілки ліворуч ↔ праворуч | — |
| Вібрація | вимк / слабка (×0,6) / сильна (×1,4) | — |

Позиція зберігається у **частках безпечної зони**, а не в пікселях, тож
переживає поворот екрана й іншу роздільність; при розкладці все
затискається всередину `env(safe-area-inset-*)`. Блок не можна кинути
поверх самої панелі — інакше він накрив би її повзунки й дістати їх
стало б ніяк; при спробі блок відсувається до найближчого краю панелі.

**Хітбокс ніколи не менший за 125% базового розміру** — навіть коли
повзунок стоїть на 70%. Заміряно тестом `tests/ui.mjs`:

```
хрестовина: 53 px видимо / 94 px хітбокс     (база 150 px × 1,25 ÷ 2)
кнопка:     24 px видимо / 43 px хітбокс     (база  68 px × 1,25 ÷ 2)
```

## 2. Інвентар зі слотами

Два активні слоти: **один ближній (B), один дальній (C)**. Решта лежить
в арсеналі. Зміна — на чекпоінті, у паузі, перед ареною боса; опція
«Вільна зміна зброї» знімає обмеження (за замовчуванням вимкнена).
Правило перевіряється тестом: посеред бою `arc → arc` (зброя не
змінилась), з увімкненою вільною зміною — `arc → brand`.

Екран показує дві комірки, дві вкладки, сітку з п'яти іконок,
опис механіки одним реченням, три смужки (Урон / Темп / Дистанція),
ресурс і джерело. Незнайдені — темні силуети з підказкою
«Знайти на секторі N» / «Нагорода за боса N».

HUD показує іконки обох комірок і **ресурс саме тієї зброї, що в руках**:
шкала заряду для тесака, кулдаун телепорту для хронорізу, тепло й зелена
зона для рейкострила, шість набоїв для «Картечі», три ядра для Гліч-Коду,
три дрони для «Рою», ∞ для «Оси».

## 3. Звіт балансу: заміряний DPS усіх десяти зброй

`node tests/weapons.mjs` — 12 секунд по нерухомій мішені, у контакті
(12 px для ближніх, 18 px для дальніх), на дистанції 110 px і по трьох
цілях поряд.

| Зброя | Впритул | 110 px | Три цілі | Ресурс | Сильна проти | Слабка проти |
|---|---:|---:|---:|---|---|---|

## 4. Розрахунки по кожному босу

`node tests/balance.mjs`. Модель гравця: **влучає 60% ударів** (вимога ТЗ)
і **ухиляється від 85% телеграфів** — пропускає кожну сьому атаку.
5 сердець дозволяють пережити 4 влучання, тож бос має право встигнути
не більше **27 атак** за бій.

**Аналітичний DPS стартової зброї з констант гри:**

```
АРК-ТЕСАК   комбо 2+2+3 = 7 шкоди за 0,71 c              →  9,86 DPS
РЕЙКОСТРИЛ  9 пострілів × 0,13 c = 1,17 c вогню
            + 1,27 c перегріву (0,7 влучань в зелену зону) →  3,69 DPS
МІКС 40/60                                                →  6,15 DPS
× точність 60% × час на атаку 70%                         →  2,59 DPS
```

**Замір у бою** (бот б'ється лише стартовою зброєю, без службових команд;
«атак/с» — скільки телеграфів бос піднімає за секунду, залп в межах
0,25 с рахується як одна атака):

| Бос | HP | Бот убив за | Атак/с | Атак за бій | Пропустить із 4 | Стеля HP | Вердикт |
|---|---:|---:|---:|---:|---:|---:|---|
| СЕРВОТАВР | 75 | 20,9 c | 0,29 | 6 | 0,9 | 333 | ✓ великий запас |
| МАТКА-РІЙ | 110 | 42,1 c | 0,40 | 17 | 2,6 | 173 | ✓ |
| ХРОНОКЛИНОК | 145 | 41,0 c | 0,34 | 14 | 2,1 | 276 | ✓ |
| ГЛІТЧ-ЯДРО | 110 | 80,5 c | 0,30 | 25 | 3,7 | 120 | ✓ на межі |
| АРХІТЕКТОР | 240 | 42,2 c | 0,47 | 20 | 3,0 | 320 | ✓ |

### Де довелось зменшити HP замість підняття шкоди гравця

ТЗ просило `75 / 110 / 145 / 180 / 240`. Чотири з п'яти стоять як
замовлено. **Гліч-Ядро довелось опустити 180 → 110** — і ось чому:

```
При 180 HP бій тривав 115 c: ядро велику частину часу невразливе
(вікна «перезавантаження»), тож HP переводиться в час гірше, ніж
у решти босів — 1,56 DPS проти 3,5-5,7 у сусідів.
115 c × 0,29 атаки/с = 33 атаки за бій
33 × 15% пропущених = 5,0 влучань > 4 сердець  →  бій програний до кінця

Спроба 145 HP:  97 c → 29 атак → 4,4 влучання. Так само за межею.
Спроба 130 HP:  77-102 c → 20-29 атак → 3,1-4,3. Хитається через
                випадкові ефекти арени (інверсія гравітації, зникнення
                платформ), інколи вискакує за планку.
Прийнято 110 HP: 80 c → 25 атак → 3,7 влучання з 4. Стабільно в межах.
```

За вказівкою ТЗ («зменш HP, а не збільшуй урон гравця») шкоду зброї не
чіпали — просто менше HP. У версії 1.x у цього боса було 72 HP, тобто
проти минулого кроку він усе одно **на 53% міцніший**.

Інші правки за ТЗ:
- **Не більше 1 серця за раз.** Розгін Сервотавра й ривок Архітектора у
  фазі 1 знімали по два — обидва опущені до одного.
- **Виняток у фазі 3 Архітектора** (єдиний дозволений ТЗ): падаючі уламки
  арени знімають два серця, зате мають найдовший телеграф у грі — 2,2×
  базового, тобто 0,70 с.
- **Режим люті** після 90 с: пауза між атаками ×1/1,15, телеграфи не
  чіпаються (`RT()` у `core.js`).
- **Полегшений режим**: +2 серця й телеграфи ×1,25 (`TEL()`).
- У кожного — три фази й новий патерн у фінальній: ланцюг із двох ударів
  лапою (Сервотавр), пікірування на гравця (Матка), друга тінь з іншою
  затримкою (Хроноклинок), сітка лазерів замість пари (Гліч-Ядро),
  велетенська голова й арена, що осипається (Архітектор).

## 7. Розумніший, але чесний ШІ

Спільний шар (`aiCommon`) для всіх типів:

- **Детектор краю**: промінь униз на 20 px попереду. Нема підлоги —
  зупиняється; є куди приземлитись у трьох тайлах — стрибає. Ніхто не
  падає в яму випадково.
- **Стани**: спокій → підозра (знак `?`, 0,6 с) → бій (знак `!` поки
  триває реакція) → втратив ціль (шукає 3 с в останній відомій точці,
  знак `?` згасає). Маркери малюються над головою.
- **Час реакції 250 мс** — вороги не читають думки.
- **Токен атаки**: одночасно атакують максимум двоє, решта займають
  позицію.
- **Фланг**: другий і далі заходять з іншого боку, а не в чергу.
- **Ухиляння від замаху**: 30% у звичайних, 55% у елітних.
- **Не штовхаються**: тримають 14 px один від одного.

**Реакція на зброю гравця й чому вона саме така.** Перша версія
розганяла всіх із лінії зарядженого пострілу зі 100% імовірністю — і
заряджений постріл ставав нікчемним: жоден ворог не лишався на місці.
Тест `mechanics.mjs` це і зловив («заряджений постріл пробиває щит»
провалився: щит 8 → 8 HP). Тепер кидок монети робиться **рівно один раз
на кожне заряджання** і лише для тих, хто справді стоїть на лінії
променя: 30% у звичайних, 55% у елітних, а важкі (щитоносець, ковадло,
турель, пілон, павук) не відскакують узагалі. Після правки той самий
тест дає 8 → 4.

Інше: побачили дробовик зблизька — тримають дистанцію; побачили
перегрів — тиснуть.

**Обмеження чесності** (`mayShoot`): не більше 6 ворожих куль у польоті
одночасно; ворог поза екраном не стріляє; при появі на екрані мовчить
0,5 с; жодної атаки без телеграфа.

- **Маркери уваги** `?` і `!` — окремі спрайти над головою ворога.

запікається в один атлас: 512×1024, 152 кадри, 64 КБ.

# Версія 4: анімація, видача зброї за рівні, саундтрек

## 1. Чому героїня «бігла» стоячи

Перевірив усі чотири підозри з ТЗ окремими замірами (`tests/anim.mjs`,
чернетки діагностики в тому ж стилі). Винних виявилось **двоє** — одна
з переліку і одна, якої в переліку не було.

### Підозра 1 — залипання вводу з D-pad. **ВИНЕН**

Не ковзання й не `touchcancel` — ті шляхи оброблялись правильно.
Замір показав:

| Сценарій | `S.ax` після того, як палець прибрано | Вердикт |
|---|---|---|
| ковзання з → на ← і відпускання на ← | 0 | чисто |
| `touchcancel` замість `touchend` | 0 | чисто |
| два пальці, знімаємо той, що на хрестовині | 0 | чисто |
| пауза під час утримання → | 0 | чисто |
| **згортання застосунку під час утримання →** | **1** | **ЗАЛИПЛО** |

Коли застосунок згортають з пальцем на стрілці, Android з'їдає
`pointerup`: подія просто не приходить. Прапорець напрямку лишався
натиснутим назавжди — героїня бігла без жодного дотику, а біля стіни це
й читається як «біг на місці».

**Виправлено:** одна функція `resetInput()` у `src/input.js` обнуляє
геть усе — `kb`, стан хрестовини, кнопки дій, чергу ривка, мапу
вказівників, фронти в `S`. Викликається з `blur`, `visibilitychange`,
`pagehide`, `touchcancel`, а також із `Input.enable(false)`, тобто на
кожній паузі й кожному екрані меню. Додано слухач `lostpointercapture`,
якого не було.

### Підозра 2 — швидкість ніколи не стає нулем. **НЕ ВИНЕН, але підстраховано**

Замір: після відпускання `vx` доходить до **рівно 0** за 16 кадрів
(`DEC` доїдає залишок цілком, `if (Math.abs(P.vx) <= fr) P.vx = 0`).
Хвоста на кшталт 0,0003 не було. Мертву зону з ТЗ усе одно додав —
без вводу все, що менше **5 px/с**, примусово стає нулем.

### Підозра 3 — стан за швидкістю, а не за наміром. **ЧАСТКОВО ВИНЕН**

Умова бігу була `Math.abs(P.vx) > 12` без жодної перевірки вводу, тож
ковзання по інерції, віддача дробовика, відкидання від удару й конвеєр
крутили анімацію бігу. Тепер біг вимагає **три умови разом**: є намір
(`S.ax`), персонаж на землі, `|vx| > 10`. Ковзання по інерції — це IDLE.

### Підозра 4 — лічильник кадрів крутиться завжди. **ВИНЕН**

`P.animT += dt` виконувався щокадру незалежно від стану, тож біг ніколи
не починався з першого кадру. Тепер таймер живе всередині стану й
обнуляється на кожному переході (`setAnim()`).

### П'ята причина, якої не було в переліку. **ВИНЕН, і найпомітніший**

Героїня, що спокійно стоїть, **кожні три кадри відривалась від землі**:

```
кадр  y        vy     onGround  anim
 0    194.000   0.00     1       idle
 1    194.214  12.83     0       fall     ← гравітація штовхнула на 0,21 px
 2    194.642  25.67     0       fall     ← 0,64 px — зіткнення ще не помічене
 3    194.000   0.00     1       idle     ← аж тепер відкотило назад
```

`moveY()` перевіряв нижню грань із відступом у **цілий піксель**
(`Math.floor((y + h - 1) / TS)`), тож коробка встигала зануритись у
підлогу майже на піксель, перш ніж зіткнення реєструвалось. Наслідок —
`onGround` миготів 1-0-0 з частотою 20 Гц, а спрайт сіпався між
спокоєм і падінням. Відступ замінено на **EPS = 0,01** (менший за крок
гравітації за кадр — 0,39 px), а прив'язку після зіткнення переписано
на «ряд, з яким реально зіткнулись», бо стара формула залежала від того
самого цілого пікселя.

Після виправлення: **0 кадрів у повітрі зі 120** у стані спокою, стан
весь час IDLE, кадри лише `idle` і `blink`.

## 2. Машина станів анімації

Єдина точка переходу — `setAnim(newState)` у `src/core.js`; вона
обнуляє таймер і номер кадру. Прямих присвоєнь `P.anim` у коді більше
немає (перевірено пошуком: лишилось одне — початкове значення при
створенні гравця).

```
                 ┌──────────────────────────────────────────┐
                 ▼                                          │
  IDLE ──намір+vx>10──► RUN ──втратив опору──► JUMP/FALL ──приземлення──► LAND
   ▲                     ▲                                                 │
   └─────── 0,12 с ──────┴─────────────────────────────────────────────────┘
   ▲
   ├── CROUCH  (↓ на землі)
   ├── DASH    (ривок)
   ├── ATTACK  (atkT > 0)
   ├── HURT    (hurtT > 0)
   └── DEAD
```

Пріоритети рівно з ТЗ, реалізовані числами в `AST` — стан обирається
першим збігом згори вниз:

| Стан | Пріоритет | Умова | Кадр |
|---|---:|---|---|
| DEAD | 90 | `P.dead` | `hurt` |
| HURT | 80 | `hurtT > 0` | `hurt` |
| ATTACK | 70 | `atkT > 0` | `atk` |
| DASH | 60 | `dashT > 0` | `jump` |
| JUMP | 50 | не на землі, летить угору | `jump` |
| FALL | 45 | не на землі, летить униз | `fall` |
| LAND | 30 | 0,12 с після приземлення | `land` |
| CROUCH | 25 | присів на землі | `crouch` |
| RUN | 20 | **намір І на землі І `\|vx\| > 10`** | `run1-3`, темп від швидкості |
| IDLE | 10 | усе інше | `idle` / `blink`, **6 fps** |

**IDLE** тримає власний лічильник простою: дихання, гойдання шарфа,
кліпання раз на 2,4–5 с. Через **5 секунд** бездіяльності вмикається
довга анімація — Ехо піднімає хромовану руку й поправляє протез
(`idle2a`/`idle2b`, 1,6 с), потім лічильник обнуляється й усе
повторюється.

**LAND** — 0,12 с присідання, далі стан вирішується сам: якщо тримають
напрямок, одразу RUN, якщо ні — IDLE.

### Звіт по п'яти ситуаціях

Відпускаємо геть усе й міряємо, за скільки кадрів настане IDLE
(`node tests/anim.mjs`). Час падіння — не вина анімації, тому поряд
іде число «від моменту, коли ноги торкнулись землі»; ліміт ТЗ 0,2 с =
12 кадрів застосовано саме до нього.

| Ситуація | Кадрів усього | Від приземлення | Час | Ланцюг станів |
|---|---:|---:|---:|---|
| на землі (біг →) | 1 | 1 | 0,017 c | IDLE |
| у повітрі (стрибок) | 16 | 8 | 0,133 c | FALL → LAND → IDLE |
| під час атаки | 10 | 10 | 0,167 c | ATTACK → IDLE |
| після ривка | 1 | 1 | 0,017 c | IDLE |
| після виходу з паузи | 1 | 1 | 0,017 c | IDLE |

Плюс окремо перевірено те, про що просив ТЗ наприкінці:

```
✓ рух (хрестовина →): після згортання ввід не залипає   S.ax = 0
✓ стрільба (кнопка C): після згортання ввід не залипає  S.c = false
✓ стоячи на місці, героїня жодного кадру не відривається від землі (0 зі 120)
✓ через 5 с простою вмикається довга анімація
```

### Три фрагменти Ехо-Призми — точні координати

Кожен лежить у секретній кімнаті свого сектора (та сама схованка, куди
раніше клали дата-лог), за платформенною ділянкою, яку видно, але треба
постаратись:

| Сектор | Тайл | Піксель | Де саме |
|---|---|---|---|
| **3** «Дахи сектора» | (75, 5) | (1200, 80) | схованка над дахами: заскочити на платформу ряду 6 і піднятись у нішу під стелею |

| **9** «Шпиль Кайзен-Вольт» | (211, 5) | (3376, 80) | остання схованка перед ареною, вище основного маршруту |

Підказка чесна: біля фрагмента **блакитне мерехтіння** (пульсуюче
світло + три іскри, що піднімаються) і власний стінгер при підборі.
Лічильник у головному меню: «ФРАГМЕНТИ ПРИЗМИ: N / 3». Зібрав усі три —
на **найближчому чекпоінті** призма збирається сама, з окремим
спалахом і стінгером.

**Механіка:** постріл коштує ядро (3 шт., ті самі, що в Гліч-Кода),
відбивається від стін до **5 разів**, і на кожному відбитті
**роздвоюється** без втрати шкоди. Замір: один постріл у коридорі
сектора 1 дав **8 променів** і витратив усі 5 відбиттів. На відкритій
місцевості промінь просто вилітає за екран — там вона майже марна,
це її чесний мінус.

Гра проходиться повністю без призми: жодна нагорода й жоден прохід від
неї не залежать.

| Шар | Що додається | Коли |
|---|---|---|

| 1 | + drums | ворог помітив або поряд |
| 2 | + arp lead | бій |
| 3 | + подвійний темп і драйв | бос, фінальна фаза |

губиться й нічого не клацає. Заміряно:

```
шар 2 → рівень 2   гейни 1.00/0.90/0.85/0.00
шар 3 → рівень 3   гейни 1.00/0.90/0.85/0.80
шар 1 → рівень 1   гейни 1.00/0.90/0.00/0.00
```

**Мікшер:** окремі повзунки «Ефекти» і «Музика», 0–100% із кроком 5%,
поточний трек видно тут же в налаштуваннях. Старі збереження (шкала
0–10) конвертуються автоматично.

**Ducking** −25% на появі боса, при видачі зброї та знайденому секреті:
0,850 → 0,637 на шині (заміряно).

**Контекст стартує лише після дотику.** Сам модуль Tone підвантажується
динамічним `import()` уже в обробнику жесту — інакше сам факт імпорту
створює AudioContext, і Chrome пише попередження ще до першого кліка.
На згортанні Transport стає на паузу, на поверненні музика підіймається
за 0,4 с. Заміряно: `started → paused → started`, сигнал на шині
−19,7 dBFS без кліпінгу.

**Про синхронізацію атак боса з тактом.** Свідомо не робив: щоб
покласти замахи на долю, довелося б зсувати таймери атак, а промт
прямо забороняє чіпати баланс босів (він заміряний і зафіксований у
попередньому кроці). Натомість темпи треків підібрані під характер
кожного бою — 140 BPM під ривки Сервотавра, 155 із ламаним ритмом під
Гліч-Ядро.

# Версія 5: прив'язка спрайтів, читабельність, легші боси, хлист

## 1. Чому героїня втопала в підлогу

Перевірив усі п'ять підозр із ТЗ. Винна **друга**, і з'ясувалось це першим
же заміром — порівнянням розмірів спрайта з хітбоксом для героїні й
кожного ворога окремо:

```
тип       хітбокс   спрайт    різниця
герой     10x14     16x22     8 px НИЖЧЕ НІГ   <-- ось воно
skreb     12x9      12x9      0
thug      12x15     12x15     0
turret    14x14     14x14     0
...усі 18 типів ворогів      0
```

Спрайт героїні малювався з `anchor (0,0)` у точці `P.y`, тобто верхній
лівий кут спрайта збігався з верхнім лівим кутом хітбокса. Хітбокс 14 px,
спрайт 22 px — уся різниця у 8 px ішла **вниз**, у підлогу. Вороги не
тонули, бо в них спрайт і хітбокс збігаються піксель-у-піксель.

**Що з рештою підозр:**

| # | Підозра | Вердикт |
|---|---|---|
| 1 | Точка прив'язки | не була причиною сама по собі, але виправлена разом із #2: тепер `anchor (0.5, 1.0)` для героїні, фантома й **усіх** ворогів |
| 2 | **Спрайт вищий за хітбокс, різниця йде вниз** | **ВИНЕН** |
| 3 | Неповне розв'язання колізії | ні: `y` при спокої стабільно 194.000, `vy = 0`, `onGround = 1` кожен кадр (це вже виправлено в промті №6 заміною відступу колізії на EPS = 0,01) |
| 4 | Округлення при масштабуванні | ні: і камера, і позиції спрайтів уже йшли через `Math.round` |
| 5 | Візуальний край ≠ колізійний | ні: тайл малюється в `tx*TS, ty*TS`, неонова смуга — у рядках 0-1 самого тайла, верх збігається з верхом колізії |

**Виправлення.** Одна функція `putEnt()` у рендері: `anchor (0.5, 1)`,
`x = центр хітбокса`, `y = низ хітбокса`, все округлено. Через неї тепер
малюються героїня, фантом і всі вороги — жодних ручних `s.x += 12`.

Разом із цим **героїню повернуто до старого спрайта 12×15** (розділ 3),
тому різниця зі спрайтом тепер 1 px і йде вгору, у маківку.

### Що видно в режимі хітбоксів

Налаштування → **Хітбокси (розробнику)** → «Показати». Малює:
червоним — хітбокси героїні, ворогів і всіх частин боса; зеленим — сітку
тайлів (тверді підсвічені яскравіше, платформи блакитним, шипи червоним);
жовтою лінією на всю ширину екрана — рівень підлоги під героїнею; унизу
два рядки цифр: `ХІТБОКС 10x14  СПРАЙТ 12x15` і
`НИЗ ХІТБОКСА y=208.0   ПІДЛОГА y=208.0   onGround=1`.

**Було:** нижня грань червоної рамки стояла на жовтій лінії, а спрайт
звисав на 8 px нижче — ноги, чоботи й частина куртки були під підлогою.
**Стало:** низ спрайта, низ червоної рамки й жовта лінія — один і той
самий піксель; над рамкою лишається 1 px маківки.

## 2. Пост-обробка: було → стало

| Параметр | Було | Стало |
|---|---|---|
| Bloom, поріг яскравості | 0,62 | **0,86** — світяться лише самі джерела |
| Bloom, сила | 0,90 | **0,35** (повзунок 0-100%) |
| Bloom, радіус | 5,0 / 3,0 | **2,5 / 1,6** — удвічі менший |
| Хроматична аберація | завжди 0,4 + сплески | **вимкнена** (0%); сплеск 0,15 с при шкоді й фон на арені Гліч-Ядра |
| Тонування кадру (тіні) | `grade × 0.5` | `grade × 0.18` |
| Тонування кадру (світло) | `× (0.97 + grade × 0.45)` | `× (1.0 + grade × 0.09)` |
| Насиченість | 1,06 | 1,00 |
| Фон (небо, силуети, відбиття) | ті самі яскравість і насиченість, що й гра | окремий шар: **яскравість 60%, насиченість −25%** |
| Контур силуетів | не було | **1 px темний** (`#0a0612`) навколо героїні й усіх ворогів |
| CRT | вимкнено | вимкнено (лишилось) |

Помаранчева пелена йшла саме з рядка `col += grade * (1.0 - lum) * 0.5` —
колір локації додавався до всього кадру. Тепер тонуються тільки тіні й
утричі слабше.

**Як тепер виглядає кадр.** Фон — темні фіолетові силуети міста, помітно
глухіші за ігровий шар. Підлога читається однією яскраво-рожевою смугою
по верхньому краю тайлів: видно, куди приземлишся. Героїня — суцільна
рожево-фіолетова пляма з темним контуром, помітна навіть на фіолетовій
підлозі. Світяться лише самі джерела: вивіски, кулі, клинок, кінчик
хлиста. Кольорового розшарування на спрайтах немає.

**Нові повзунки** в Налаштуваннях: Bloom 0-100%, Аберація 0-100%,
Яскравість фону 20-100%, Scanlines/CRT так/ні, Контур силуетів так/ні,
Хітбокси так/ні. Плюс кнопка **«Чистий режим»** — вимикає bloom,
аберацію й CRT, піднімає фон до 75% і лишає контури. Перевірив: у
чистому режимі картинка не розвалюється — це той самий піксель-арт,
просто без світіння, і читається він навіть краще.

## 4. Електрохлист і решта зброї

**Хлист** — мотузка з **12 ланок по 6 px** (загалом 66 px). Форма
будується ланка за ланкою від рукояті: кожна наступна відхиляється на
невеликий кут, тому довжина між вузлами завжди рівно 6 px і мотузка не
заплутується; згори — згладжування з різним коефіцієнтом (рукоять
швидка, кінчик відстає) і жорстке обмеження довжини. Хвиля розпрямлення
біжить від рукояті до кінчика, тож ланки випрямляються **по черзі**.

Заміряні позиції кінчика відносно героїні (dx, dy) по кадрах:

| Кадр | Стадія | Кінчик dx | dy | Довжина |
|---:|---|---:|---:|---:|
| 2 | замах | +18 | −16 | 26 |
| 4 | замах | +13 | −35 | 42 |
| 6 | замах | **−14** | −32 | 43 |
| 8 | викид | −33 | −11 | 41 |
| 12 | викид | −38 | −22 | 51 |
| 14 | викид | −7 | −36 | 44 |
| 16 | викид | +28 | −28 | 41 |
| 18 | викид | **+47** | −8 | 45 |
| 20 | повернення | +55 | −14 | 54 |
| 26 | повернення | +52 | −26 | 57 |

- **Замах 0,12 с** — хлист збирається за спиною й над плечем.
- **Викид 0,18 с** — дуга проходить від −41 до +55 px, ланки
  розпрямляються по черзі.
- **Повернення 0,15 с** — зупиняється попереду й провисає (dy росте).

Товщина від **3 px біля рукояті до 1 px на кінчику**. Уздовж мотузки
біжать білі розряди, кінчик світиться яскравіше за решту й має власне
світло. На переході «замах → викид» — короткий білий спалах по всій
довжині (0,08 с). Дуга лишає **шлейф із 14 точок, що згасає за 0,2 с**.
У точці удару — іскри, відкидання ворога й **видима блискавка** ламаною
між ураженим і наступним ворогом, коли розряд перестрибує.

**Хітбокс — сама крива**: перевіряються три точки на кожній ланці, а не
прямокутник. Гравець б'є рівно тим, що бачить. Звук: свист розсікання на
замаху (`Sfx.dash`) і електричний тріск при контакті (`Sfx.parry`) —
два різні семпли.

Баланс після переробки (заміряно `tests/weapons.mjs`): **3,6 DPS по
одному, 8,4 по трьох** — роль «зброя для натовпу» збережена, ціна —
0,45 с на повний удар замість 0,26.

**Решта зброї, як тепер виглядає:**

- **Арк-тесак** — біла дуга поперек напрямку удару; третій удар комбо
  жовтий і вдвічі товщий.
- **Тавро** — товста помаранчева смуга (6 px) і при зарядженому ударі
  **хвиля пилу по підлозі**: 12 піщаних частинок з кожного боку летять
  попереду ударної хвилі, показуючи, куди вона йде.
- **Плазмові кігті** — **три короткі паралельні розрізи** бірюзою, кожен
  зі своїм зсувом по вертикалі й білою серцевиною.
- **Хроноріз** — фіолетовий спалах у точці входу й виходу телепорту.
- **Дробовик «Картеч»** — **конус із 6 трасерів**: кожна дробина малюється
  трьома згасаючими сегментами вздовж польоту, плюс **сірий дим із дула**
  (10 повільних частинок).
- **Рій** — три дрони з **видимою траєкторією**: за кожним тягнеться слід
  із 10 точок, ціль позначена чотирма кутиками.
- **Ехо-Призма** — блакитний промінь із яскравим слідом; на кожному
  відбитті кільце й роздвоєння.
- **Гліч-Код** — бірюзовий контур і пульс навколо перехопленого ворога.

# Версія 7: Гліч-Ядро стало досяжним

## 1. Чому по ньому не можна було влучити

Числа, а не відчуття. Ядро на час перезавантаження опускалось на `y = 138`
з хітбоксом 26 px — тобто займало смугу **138..164**. Дуга клинка по
вертикалі дорівнює тілу героїні (14 px), і у вершині стрибка з підлоги
вона накриває **127,9..141,9**.

Перетин: **3,9 px**. І це ще не все — під час того самого вікна ядро
**не переставало їздити по горизонталі** (`sin(anim·0.45)·96`), а
контактна шкода лишалась увімкненою. Тобто треба було влучити в
4-піксельну смугу, на вершині стрибка, по цілі, що рухається, і не
торкнутись її при цьому. Формально можливо, практично — ні.

| **АРК-ТЕСАК**, комбо ×3 | **37** |
| **РЕЙКОСТРИЛ**, швидкі тапи | 15 (перегрів з'їдає пів вікна) |
| **РЕЙКОСТРИЛ**, заряджені постріли | **17** |

**HP боса: 95 → 60.** Причина саме та, яку ТЗ і називає: дальня зброя
впиралась у стелю «не більше 6 вікон». При 95 HP рейкострил вимагав
6 вікон за формулою, але **136,8 с** у реальному бою — удвічі більше за
ліміт у 90 с. Урон гравцеві не чіпали, зменшили HP боса.

| | вікон (HP / шкода за вікно) | бій ботом | вікон у бота |
|---|---|---|---|
| тільки клинком | **2** | **10,0 с** | 4 |
| тільки рейкострилом | **4** | **68,1 с** | 9 |
| мікс (арк + рейкострил, бот із `balance.mjs`) | — | **62,6 с**, пропускає 1,7 з 4 сердець | — |

Формула дає ідеальний випадок — гравець заходить у кожне вікно з нульовим
теплом. Бот так не вміє: він приходить розігрітим, тож витрачає більше
вікон. Обидва числа в таблиці навмисно, бо чесні вони тільки разом.

Обидва варіанти — і тільки ближня, і тільки дальня — проходяться й
вкладаються в 90 с.

## 6. Аудит усіх п'яти босів

Питання: чи є в кожного боса гарантоване вікно, коли до нього дістає
ближня зброя. Зона ураження клинка з поверхні на висоті `sy` — це смуга
`[sy − 14 − 66,1, sy]`: за один стрибок тіло героїні (а з ним і дуга)
проходить усі ці висоти, не тільки вершину.

| Бос | HP | Вікно відкривається | Вразлива зона | Дістає клинок | Запас | У зоні | Найдовша пауза |
|---|---|---|---|---|---|---|---|
| СЕРВОТАВР | 55 | постійно | 178..208 | так | 30 px | 100 % | 0 с |
| МАТКА-РІЙ | 75 | постійно | 94..206 | так | 24 px | 72 % | 2,5 с |
| ХРОНОКЛИНОК | 95 | раз на 3,5 с (парирування) | 186..208 | так | 22 px | 100 % | 0 с |
| ГЛІТЧ-ЯДРО | 60 | раз на 3 с | 112..187 | так | 48 px | 100 % | 0 с |
| АРХІТЕКТОР | 150 | постійно | 80..208 | так | 52 px | 100 % | 0,6 с |

**Виправлено одного, крім Гліч-Ядра: МАТКУ-РІЙ.** Поки живий хоч один
генератор, матка невразлива, а кожен збитий генератор опускав її на 3 с у
зону клинка — але **після останнього генератора опускань більше не
було**, і вона лишалась висіти на `y ≈ 94..114`, недосяжною для ближньої
зброї до кінця бою. Тепер, коли генераторів не лишилось, вона сама
сідає в зону ураження **на 2,5 с раз на 6 с** (зі спалахом і звуком —
це видиме вікно, а не випадковість).

Решту не чіпали:
* **Сервотавр** б'ється на підлозі — вразливий постійно.
* **Хроноклинок** відкривається на `stagger` після парирування, стоїть
  на підлозі, вікно раз на 3,5 с.
* **Архітектор**: у фазі 2 три ядра крутяться по орбіті `y = 124 ± 44`
  і щонайбільше 0,6 с поспіль бувають вище за дугу клинка — цього мало,
  щоб вважати боса недосяжним.

## 1. Керування: лишились тільки ← і →

Хрестовина з чотирьох стрілок була анахронізмом: ↑ дублювала кнопку `A`,
а ↓ тільки заважала великому пальцю.

| | Було | Стало |
|---|---|---|
| стрілок | 4 (↑ ↓ ← →) | **2 (← →)** |
| розмір однієї | 75×75 CSS-px | **90×120 CSS-px** |
| проміжок | спільна підкладка | **10 px, підкладки нема** |
| хітбокс | +25 % | **+30 % і нахилений усередину** |
| стрибок | `A` **або** ↑ | **тільки `A`** (на ПК ще пробіл/W/↑) |
| ковзання ←→ | працює | працює (межа рівно посередині) |

**Нахил усередину.** Великий палець крутиться навколо нижнього кута
екрана й угору йде по дузі, а не по прямій. Тому хітбокс не просто
прямокутник: `padDirs()` зсуває координату пальця на `ay · 0,18` до
центра екрана, і верх зони «їде» слідом за дугою пальця на +11 px
(`CONFIG.DPAD_TILT`). Межа між ← і → нахилена так само, тож ковзання з
однієї стрілки на другу лишається без відриву на будь-якій висоті.

Перетягування блоку, повзунки розміру (70–160 %) і прозорості
(20–100 %), пресети й дзеркальна розкладка з промта №5 працюють як
раніше — вони рахуються від нової коробки 190×120 автоматично.

вертикальних відгалужень. Обрано другий варіант — **утримання `A`

Як це працює, щоб не зачепити фізику стрибка:

* коротке натискання `A` — це, як і було, звичайний стрибок;
* лічильник `P.dropHold` іде **тільки поки героїня стоїть на тонкій

* свіже натискання не встигає нічого накопичити: воно миттєво відриває
  героїню від землі, і лічильник обнуляється сам;
* за 0,15 с до спуску з-під ніг сиплеться пил — видно, що зараз
  провалишся;
* після спуску лічильник скидається, тож пролетіти три платформи
  поспіль одним утриманням не можна.

На практиці: тап `A` (стрибок) → тримаєш далі → приземлення на ту саму
платформу → ще 0,4 с → провал. Заміряно в тесті: **1,22 с** від
натискання. Тапи по `A` не провалюють жодного разу — перевірено окремо.

## 5. Матка-Рій: оси прив'язані до генераторів

Було: матка сама випускала осу раз на 2,5 с, поки живих дронів менше
трьох. Генератори при цьому були просто «замками» на щиті — бій читався
як два незалежні правила.

Стало:

* **матка не спавнить нікого.** Оса виходить **із конкретного вузла**;
* кожен живий генератор випускає одну осу **раз на 4 с**, з розбіжкою
  фаз, щоб вони не сипались залпом;
* збитий генератор **не спавнить більше ніколи** — потік звідти
  припинився назавжди;
* стеля — **4 оси на екрані** одночасно, скільки б генераторів не було;
* від кожного живого вузла до матки тягнеться **світловий кабель** із
  провисанням і біжучим імпульсом. Вузол мертвий — кабель темніє й
  провисає сильніше: прогрес видно без жодного тексту;
* на випуску вузол здригається, підстрибує на 2 px і спалахує;
* матка невразлива, поки живий хоч один вузол (як і було), і опускається
  на 3 с після кожного збитого — вікно для ближньої зброї.

**Перерахунок складності** (бот б'ється лише Арк-тесаком і
Рейкострилом, точність 50 %, ухиляння 85 %):

| | Було (промт №7) | Стало |
|---|---|---|
| HP | 75 | 75 (не чіпали) |
| час бою бота | 22,6 с | **27,0 с** |
| атак боса за бій | 8 | **9** |
| очікувано пропустить | 1,2 з 4 | **1,4 з 4** |
| стеля HP при цьому темпі | 250 | **222** |

Бій став на 4,4 с довшим, бо оси тепер ідуть звідусіль, а не з однієї
точки, — але запас лишився майже подвійний (пропускає 1,4 з 4 сердець).

## 7. Катсцени: архітектура

`src/cutscene.js` — сценарій це масив кроків, кожен крок має одне
«дієслово»:

```js
{ say:'…', by:'ЕХО', p:'p_echo', t:2.6, anim:'slide' }  // репліка з портретом
{ p:'p_servotaur', anim:'rise', t:0.8 }                 // тільки показати портрет
{ cam:{ dx:46 }, t:0.9 }                                // наїзд камери (відносний)
{ wait:0.6 }                                            // пауза
{ shake:5 }                                             // тряска
{ music:{ track:'boss2', layer:3, duck:2.0, sting:'boss' } }
{ flash:0.35 }                                          // спалах
{ fade:'out', t:0.5 } / { fade:'in', t:0.5 }             // перехід
{ sfx:'bossIn' }                                        // звук
```

* **Портрет боса й анімація появи** — поля `p` і `anim`; анімацій чотири:
  `slide` (виїжджає збоку), `rise` (піднімається знизу), `glitch`
  (збирається з перешкод), `fade`.
* **Тригери**: `pre:<рівень>` — перед боєм з босом, `post:<рівень>` —
  після його смерті, `lvl:<рівень>` — на початку рівня. Ключ шукається в
  `SCRIPTS`; якщо сценарію нема, `playCut()` одразу викликає callback,
  тож порожній тригер не може підвісити гру.
* **Пропуск у будь-який момент** — один тап (чи клавіша) будь-де,
  ловиться на capture, щоб шар керування не з'їв подію. Підказка
  «ТАП — ПРОПУСТИТИ» видно постійно, перші 3 с яскравіше.
* **Другий перегляд не обов'язковий**: переглянуті id лежать у
  `Store.data.seenCuts`, і вдруге катсцена не показується взагалі
  (`cutAlways` вмикає повтори, якщо колись знадобиться).
* **Під час катсцени** `Game.state === 'cut'`: `stepGame` не викликається
  (гра стоїть), `Input.enable(false)` ховає керування й блокує ввід,

# Версія 8: правки після повного проходження

Шість зауважень із живої гри. Сюжет, музику, керування й режим бога не
чіпав — правки торкнулись тільки наведення, анімації, балансу дробовика,
Хроноклинка, розміру спрайтів і камери.

## 1. Автонаведення нарешті бачить босів

Причина була дурна й тому довго не помічалась: пошук цілі ходив по
масиву `ENEM`, а боси живуть в окремому об'єкті `BOSS` зі своїми
хітбоксами. Для «Оси», дронів «Рою» і сканера боса просто не існувало —
куля пролітала крізь Сервотавра й доводилась до дрібного скреба за ним.

Полагоджено не латкою в кожній зброї, а одним спільним списком цілей.
`targets()` збирає в один масив усе, у що взагалі можна цілитись, і
кожен елемент описується однаково: коробка, чи живий, і пріоритет.
`pickTarget(x, y, dx, dy, дальність, конус)` — єдина точка вибору;
`homeBullet`, `osaScan` і `launchDrone` тепер лише викликають її.

**Пріоритети, від вищого до нижчого:**

| Пріоритет | Що це | Чому саме так |
|---|---|---|
| 5 | відкрита вразлива зона боса | якщо бос сам відкрився — б'ємо туди й ніде більше |
| 4 | корпус боса без броні | головна ціль на арені |
| 3 | звичайний ворог | звичайна робота |
| 2 | генератор, вузол даних | збивати їх треба, але вони не б'ються у відповідь |
| 1 | бос під бронею | остання ціль: шкоди не буде, але куля хоч летить у бік боса |

Останній рядок і був справжньою проблемою. Наведення чесно веде кулю в
броньованого боса, шкоди нема — і здається, що зброя зламана. Тепер у
такий момент на місці влучання спалахує перекреслений щиток
(`wfx({k:'armor'})`), а рамка сканера стає червоною. Видно не «зброя не
працює», а «сюди зараз не можна».

## 2. Своя анімація атаки під кожну зброю

Раніше всі одинадцять зброй грали одну спільну позу `atk`, мінявся лише
ефект. Тепер героїня рухається по-різному: **38 нових поз, по 3-4 кадри
на зброю**.

Пози не намальовані сітками крапок. Кожна — це базова фігура плюс
кілька правок: рука туди, корпус нижче, плечі в розворот. У коді видно
намір кадру («присів і б'є вниз усією вагою»), а не поле символів, яке
страшно правити.

| Зброя | Кадри | Що видно |
|---|---|---|
| АРК-ТЕСАК | `a_arcW → a_arc1 → a_arcR` | замах через плече, рубальний удар, проводка; **три РІЗНІ кадри на три удари комбо**, третій — з розворотом корпусу (`a_arc3 → a_arcT`) |
| ЕЛЕКТРОХЛИСТ | `a_whip1 → a_whip2 → a_whip3 → a_whip2` | рука назад, корпус у розворот, широкий викид з нахилом, повернення |
| ТАВРО | `a_brand1 → a_brand2 → a_brand3` | присідання з підготовкою, удар униз усією вагою, віддача в плече |
| ХРОНОРІЗ | `a_chron1 → a_chron2 → a_chron4` | низька стійка, різкий випад, проводка |
| ХРОНОРІЗ (телепорт) | `a_chron2 → a_chron3 → a_chron1` | випад крізь ворога, **поява спиною до камери**, стійка |
| ПЛАЗМОВІ КІГТІ | `a_claw2 → a_claw1 → a_claw3` | короткі випади **по черзі лівою й правою**, корпус майже не рухається |
| РЕЙКОСТРИЛ | `a_rail2 → a_rail3 → a_rail1` | постріл з упору, помітний відкид, повернення в упор ногою |
| ПІСТОЛЕТ «ОСА» | `a_osa2 → a_osa1 → a_osa3` | легка стійка однією рукою, ствол трохи гуляє, віддачі майже нема |
| РІЙ | `a_swrm1 → a_swrm2 → a_swrm3` | **не стріляє, а вказує рукою** на ціль |
| ДРОБОВИК | `a_shot1 → a_shot2 → a_shot3` | дві руки, сильний відкид корпусу назад; плюс окремий кадр `a_shotR` — цівка ходить під час перезаряджання |

**Прив'язка до реального часу.** Кадр обирається не за лічильником
кадрів, а за часткою пройденого удару, тож анімація не «наздоганяє»

## 3. Дробовик упритул сильніший за пістолет

Було навпаки, і це прямо суперечило опису зброї. Причина: дробини
розліталися конусом **із самого ствола**, тож упритул більшість
пролітала повз ворога завширшки 16 px — влучали одна-дві з шести.

Тепер шість дробин виходять **з однієї лінії**, а розліт наростає з
відстанню: кожна дробина везе `b.spreadV`, яка вмикається пропорційно
пройденому шляху (`SH.OPEN = 100 px`). Упритул конус нульовий — б'ють
усі шість; на 110 px розліт повний і дробовик стає майже марним. Жодних
змін в уроні окремої дробини.

## 4. Хроноклинок: третя фаза замість довгої шкали HP

Скарга була точна: «важкий лише через запас HP, коли навчився контрити
випади — повторення одного й того самого по дві хвилини».

**HP зменшено на 20%: 95 → 76.** Далі — час замість шкали.

### Фаза 3 (з 1/3 HP)

Щит падає **зовсім**: бити можна чим завгодно й коли завгодно,
парирування лишається бонусом, а не умовою. Натомість він
телепортується за спину.

| Правило | Значення | Де |
|---|---|---|
| силует-передвісник перед появою | **0,500 с** (заміряно на всіх 14 появах) | `CH_TEL` |
| бос з'являється саме там, де стояв силует | розбіжність 0 px | `blinkTel` |
| телепорт не частіше ніж | **раз на 2,5 с** (найкоротша реальна пауза — 4,2 с) | `CH_TP_CD` |
| двічі поспіль в ту саму точку | **ніколи** (три точки, повторів 0) | `chronoBlinkSpot()` |
| заходить саме за спину | 10 появ із 14 | дві з трьох точок — за спиною |
| влучив у момент появи | **подвійна шкода** (10 → 20) | `CH_PUNISH = 0,45 с` |

Ухилення тому обов'язково можливе: 0,5 с — це 30 кадрів, вистачає й
відскочити, і стрибнути, і зробити ривок.

### Два нові патерни фази 2

- **РИВОК через арену.** Телеграф 1,3 с на всю підлогу, потім кидок зі
  швидкістю 330 px/с. За собою лишає смугу, що ранить, — **висотою 14 px
  при висоті стрибка 66 px**, тобто перестрибується з запасом у 4,7 раза.
  Врізавшись у стіну, бос сам себе відкриває на 1,4 с.
- **ЧАСОВА КОПІЯ.** Повторює його попередню серію із затримкою 1 с:
  до 5 фантомів на арені одночасно, і стежити доводиться за двома. Поки
  копія доспівує серію, оригінал розсинхронізований і теж відкритий —
  патерн став вибором (гнатись за копією чи бити його), а не паузою.

### Перерахунок тривалості

Бот — не людина: він не промахується повз вікно й не відступає. Тому
міряємо його час на **обох версіях тим самим скриптом** (з реакцією
0,2 с), а живу гру перераховуємо від однієї відомої точки: стара версія —
33,4 с у бота й близько двох хвилин у живій грі, тобто коефіцієнт 3,6.

Коефіцієнт чесний лише для фаз зі щитом: там усе впирається в
парирування, і слабший гравець втрачає рівно стільки, скільки
промахнувся повз вікно. У третій фазі щита нема взагалі — гравець б'є,
коли хоче, і відстає від бота куди менше, тож для неї беремо 1,8.

| | ДО (HP 95, 2 фази) | ПІСЛЯ (HP 76, 3 фази) |
|---|---|---|
| час бота (6 прогонів) | 33,4 с | **21,5 с** (−36%) |
| бос відкритий | 40% часу | **50% часу** |
| фаза 2 вмикається | 15,2 с | 8,9 с |
| фаза 3 вмикається | — | 17,2 с |
| **жива гра, оцінка** | ~120 с | **70 с** |
| песимістична межа (коефіцієнт фаз зі щитом на весь бій) | — | 77 с |

Ціль 60-80 с виконано з обох боків. Рахунок ведеться до нуля HP — 2,6 с
ролика смерті це вже не бій.

## 6. Камера й кнопки

- **Героїня жорстко в центрі кадру.** Камера більше не «наздоганяє»
  плавним lerp по горизонталі — `this.x = gx` без згладжування. По
  вертикалі центр посунуто з 0,55 на 0,50 висоти: видно порівну вгору
  й униз.
- **Опція «Класична камера»** в налаштуваннях повертає старий м'який
  режим із випередженням по руху (`Store.data.cam === 1`). Арена боса
  фіксує камеру тільки в класичному режимі — у центрованому це не
  потрібно.
- **Кнопки на 20% тьмяніші в бою.** `Game.combat` вмикається, коли на
  екрані двоє й більше ворогів або йде бій із босом; `main.js` зменшує
  непрозорість шару керування. Вимикається опцією «Притлумлювати кнопки
  в бою».
## Режим розробника (`DEV_MODE`)

Інструмент, щоб пройти гру наскрізь і побачити всі рівні, босів, зброю
й катсцени. **Не читерство для гравця:** вмикається прапорцем у коді, а
в релізній збірці зникає повністю.

```js
// neon-echo/src/config.js, найперший рядок
export const DEV_MODE = true;    // у грі з'являється кнопка DBG
export const DEV_MODE = false;   // панель, чити й діагностика вирізаються зі збірки
```

Далі звичайний `npm run dev` або `npm run build`. У грі — маленька
кнопка **DBG** у верхньому куті поруч із паузою (або `F1` / `Shift+G` з
клавіатури). Гра стоїть, поки панель відкрита.

**Індикація.** Поки активний хоч один чит, по краю екрана горить червона
рамка з написом `GOD MODE`. Без неї легко протестувати баланс
безсмертним і зробити хибні висновки про складність. Діагностичні
перемикачі рамку не вмикають — вони поведінку гри не міняють.

**Правило.** Чити накладаються **поверх** базових значень і нічого не
переписують: множник урону множить нанесену шкоду, а не таблицю зброї.
Вимкнув чит — гра поводиться рівно як раніше, без залишкових ефектів.
Це перевіряється автотестом `tests/godmode.mjs`, який для кожного чита
міряє поведінку до, під час і після.

**Окремий слот збереження.** При `DEV_MODE = true` гра пише в
`echo_neon_courier_v1_dev`, тож розблокована зброя й стрибки по рівнях
не псують основний прогрес.

### Перевірка, що реліз чистий

```bash
npm run check:release
```

Скрипт збирає проєкт двічі — з `DEV_MODE = true` і `false` — і рахує в
`dist/` кожен рядок панелі й читів. Останній прогін:

```
  рядок                    DEV_MODE=true   DEV_MODE=false
  ----------------------------------------------------------
  GOD MODE                       1               0   ✓
  godFrame                       4               0   ✓
  btnDbg                         4               0   ✓
  dbgPanel                       3               0   ✓
  РЕЖИМ БОГА                     1               0   ✓
  ВБИТИ ВСІХ                     1               0   ✓
```

Працює це так: `DEV_MODE` — статична константа, кожне звернення до читів

# Версія 9: масштаб, деталізація, дробовик, рівні з характером

## 1. `SCALE` — одна константа на весь світ

Минулого разу спрайти виросли РАЗОМ із роздільністю, тож пропорція
лишилась та сама — і на екрані нічого не змінилось. Цього разу світ
росте в 1,5 раза, а кадр лише в 1,21: героїня займає на 26 % більше
екрана, і це нарешті видно.

```js
// neon-echo/src/config.js
export const SCALE = 1.5;
export const S  = v => v * SCALE;          // довжини, швидкості, прискорення
export const Si = v => Math.round(v * SCALE);
```

Правило одиниць просте: множаться **довжини, швидкості й прискорення**.
Часи, частки й одиниці шкоди не чіпаються — інакше поїде і відчуття
керування, і баланс.

| Параметр | Було | Стало | Через що |
|---|---|---|---|
| Тайл | 16 px | **24 px** | `TS = Si(16)` |
| Кадр | 528×297 | **640×360** | ×1,21, задано напряму |
| Хітбокс героїні | 13×19 | **20×29** | `Si(13) × Si(19)` |
| Сітка спрайта героїні | 16×20 | **24×30** | `HW/HH` |
| Спрайти ворогів | ×1,35 | **×2,03** | `SPR = 1.35 * SCALE` |
| Спрайти босів | ×1,5 | **×2,25** | `BSPR = 1.5 * SCALE` |
| Гравітація | 1400 | **2100** | `S(1400)` |
| Швидкість стрибка | 440 | **660** | `S(440)` |
| Другий стрибок | 330 | **495** | `S(330)` |
| Швидкість бігу | 140 | **210** | `S(140)` |
| Ривок | 300 | **450** | `S(300)` |
| Стеля падіння | 520 | **780** | `S(520)` |
| Радіус розряду клинка | 65 | **97,5** | `S(65)` |
| Швидкість кулі рейкострила | 420 | **630** | `S(420)` |
| Дальність Арк-тесака | 26 | **39** | `S(26)` |
| Дальність Електрохлиста | 76 | **114** | `S(76)` |

**Що НЕ масштабується:** розміри екранних кнопок (це CSS-пікселі, а не
світ — керування просили не чіпати), усі часи й кулдауни, усі частки й
множники, уся шкода й усе HP.

### Чому геометрія рівнів не поїхала

Бо вона міряється в ТАЙЛАХ, а тайл виріс разом з усім іншим:

| | Було | Стало | У тайлах |
|---|---|---|---|
| Висота стрибка | 66 px | **99 px** | 4,13 → **4,13** |
| Довжина стрибка | 93,2 px | 139,7 px | 5,82 → **5,82** |
| Подвійний стрибок додає | 39 px | 47 px | — |

Тобто жодна карта не переписувалась під новий розмір — і обидва
валідатори це підтвердили без жодної правки.

**Одна пастка коштувала півгодини:** параметр `S` у `meleeUpdate(dt, S)`
— знімок вводу — затінював імпортований масштаб `S()` з тим самим
іменем. Кожне завантаження рівня падало з «e is not a function».
Параметр перейменовано на `IN`.

### Множники ефектів — в одному місці

Розліт часток, радіуси кілець і розміри куль — це магнітуди, а не
позиції, тож `SCALE` застосовується просто всередині `part()`, `ring()`
і `shoot()`. Одна правка накрила понад двісті викликів по файлу.

## 3. Чому дробовик недобивав

**Обидві підозри з ТЗ не підтвердились, і це заміряно, а не вгадано.**

- **Кадри невразливості.** Їх у `damageEnemy` просто немає: п'ять
  влучань в один кадр дають п'ять порцій шкоди, а не одну (перевірка в
  `tests/shotgun.mjs`). До правок один постріл упритул уже доводив
  **5,6 дробини з 6** — і-фрейми їх не їли.
- **Ліміт шкоди за влучання.** Теж немає: сума не обрізалась згори.

Справжня причина була в двох інших речах.

**Перша — масштаб чисел.** Постріл упритул давав 6,75 одиниць там, де
удар клинка давав 2. Тобто 3,4 клинка — відчутно, але не «гармата».
Тепер уся шкода й усе HP переведені в **абсолютні числа з базовою
одиницею «один удар Арк-тесака = 10»**, як і просили:

| Зброя | Урон | Збіг із ТЗ |
|---|---|---|
| Арк-тесак (удар комбо) | 10 | еталон ✓ |
| Пістолет «Оса» | 3,5 | ✓ |
| Рейкострил | 10 | ✓ |
| Дробовик ≤30 px | **48** (6 × 8) | ✓ |

Перехід на нову шкалу — чистий перерахунок одиниць: усе помножено на 5,
включно з HP ворогів і босів, тож баланс не зрушив ні на йоту.

**Друга — постріл нічого не робив на екрані.** Тепер робить: спалах на
пів кадру, **стоп-кадр 90 мс**, сильна тряска камери, низький гуркіт під
тріском дробу, **відкидання на 52 px** і легкий ворог, який упритул
**розлітається на уламки**, а не тихо зникає. Відкидання довелось
підперти коротким приголомшенням на 0,25 с — без нього ворог перебиває
собі швидкість власним ШІ вже в наступному кадрі, і кидка не видно.

## 4. Деталізація

### Героїня: фігура, а не сітка

На 24×30 нарешті є де малювати, тож героїня більше не 12×15, розтягнуте
вдвічі. Вона **збирається зі скелета** — голова, тулуб, дві руки, дві
ноги — і кожен матеріал має **по шість тонів** замість чотирьох. Саме
тони дають об'єм: на чотирьох фігура лишається плоскою аплікацією хоч
на 24, хоч на 64 пікселях. У спокійному кадрі тепер **29 кольорів**.

Що стало видно: очі крізь візор, пасмо волосся, що падає на лице,
складки куртки, шви й підсвічена пластина на протезі, текстура
черевиків.

Поза — це положення суглобів, а не намальована сітка, тому **55 кадрів**
існують без жодного поставленого вручну пікселя. Біг — **вісім кадрів
із формули ходи**: плавно, з переносом ваги, тоді як три кадри читались
як «крок-крок». Атаки, присід приземлення й поява спиною до камери —
з того самого скелета.

**Шарф** виріс із п'яти ланок до **семи** й тепер відповідає на рух:
у спокої тягнеться на 7 px, на бігу — на **80 px**, у злеті здіймається.

**Стан здоров'я видно по персонажу:** на двох серцях і менше вмикається
окремий набір кадрів із подряпинами на куртці й іскрою з протеза.
Дивитись на смужку вгорі екрана в бою однаково ніколи.

### Вороги: три рухомі вузли на кожного

Не намальовані в кадрах, а **шари поверх спрайта** — рухома деталь
коштує два прямокутники й реагує на те, що ворог робить прямо зараз,
тоді як кадрів довелось би вчетверо більше.

| Ворог | Три деталі |
|---|---|
| Скреб | вал, що обертається; жвала; око, що блимає |
| Громила | поршень у такт; кабель, що гойдається; індикатор |
| Турель | барабан (крутиться вп'ятеро швидше на прицілюванні); радіатор; лінза |
| Оса / Камікадзе | ротор; підвіс; заряд, що пульсує |
| Щитоносець | шарнір щита; привід; лампа (зелена → помаранчева, коли щит відкритий) |
| Клинковий адепт | клинок (довший на замаху); пояс-кабель; маска (жовтіє на парируванні) |
| Павук | три лапи, що перебирають; сенсор; черево |

**Нижче 20 % HP ворог виглядає побитим:** іскри з пробитого вузла, дим
угору, осідання корпусу на крок — кульгає. На 55 % уже видно вм'ятини.
Перевірено попіксельно: побитий ворог відрізняється від здорового на
4764 байти кадру.

### Боси: живуть і видимо міняються

Поршні ходять (утричі швидше під час атаки), труби пульсують у спільний
такт дихання, кабелі гойдаються з інерцією від руху боса, а **око стежить

тримає.

**Фаза тепер ВИДНА, а не лише відчутна по темпу:**
- **фаза 2** — броня розходиться чотирма щілинами, крізь які світиться
  ядро (2185 змінених байтів кадру проти першої фази);
- **фаза 3** — ядро оголене й б'ється світлом, корпус деформується,
  підсвітка міняє колір із рожевої на помаранчеву.

### Розмір і цікавинки

Сектори розширені до **9,6–11,9 екрана** (було 6,8–9,0) не дорисованим
коридором, а **повтореним власним матеріалом**: вікно береться між двома
рівними колонками того ж рівня, тож стик непомітний, а грамотність —
платформи, ворожі групи, ритм «щось нове кожні 4–6 секунд» —
зберігається, бо це буквально його ж матеріал. Порожній коридор гірший
за короткий рівень. Унікальні мітки (спавн, вихід, тригер боса,
фрагмент Призми) у копію не йдуть.

| Цікавинка | Скільки | Як улаштована |
|---|---|---|
| **Тріснуті стіни із секретом** | 2 на сектор, 20 на гру | Ніша 3×2 в товщі підлоги за тайлом `T_CRACK`; ламає **тільки Тавро**. Усередині аптечка або дата-лог |
| **Кімнати-виклики** | 1 на сектор | Зайшов — **15 секунд**, щоб вибити чотирьох (один елітний). Устиг — дата-лог і аптечка; не встиг — просто без нагороди |
| **Пастки, що вбивають ворогів** | прес, контейнер, потяг | Усе, що давить, давить в обидва боки: `zoneCrush` б'є ворога в зоні на 999 з відкидом |
| **Голограми-підказки** | по одній на кожну механіку | **2 секунди анімації** замість абзацу: падає плита, повзе термометр, перевертається стрілка, осипається плитка. З'являється саме там, де механіка вводиться |
| **Краєвиди** | 2 на сектор | Місця, де камера відкриває місто: підсвітка неону підіймається, коли підходиш. Нічого не робиш — просто гарно |
| **Пасхалка** | рівно 1 на гру | **Аркадний автомат у метро**: на екрані крутиться демка цієї ж гри — біжить рожевий силует, повз летять платформи, унизу дві кнопки |

**Смерть не лишає в пастці.** Обвалена підлога повертається разом із
респавном, а преси, потяги й вітер скидаються у вихідний стан.

**Вітер довелось переробити з «поштовху» на «знос».** Якщо додавати його
до `vx`, його повністю з'їдає гальмування в повітрі — 450 px/с² проти
345, які додавав порив, — і на екрані не відбувається рівно нічого.
Тепер це прямий знос позиції, як течія: керування лишається, але несе.

# ВЕРСІЯ 10: МЕНЮ, РОЗКЛАДКА, НАВЧАННЯ, СКЛАДНІСТЬ

## 1. Баг: меню налаштувань було обрізане

Причина одна, і вона в CSS. `.scr` був flex-контейнером із
`justify-content: center`. Коли вміст переповнює такий контейнер, він
виштовхується **за верхній край** — і туди **неможливо прокрутити**:
`scrollTop: 0` уже найвища позиція. Заміряно до правки на 19,5:9:

```
висота екрана 405, вмісту 972, scrollHeight 707 (а не 972!)
верх вмісту: -283 px      максимальна прокрутка: 302 px
```

283 пікселі згори — заголовок, «Ефекти», «Музика», «Графіка», Bloom —
були недосяжні в принципі. Саме це й видно на скріншоті.

**Правка:** центрування через `margin: auto` на вмісті замість
`justify-content` у контейнера. Центрує так само, але при переповненні
чесно віддає прокрутку. Плюс `height: 100dvh` (не `100vh` — на Android
вона рахує екран без панелі навігації) мінус `env(safe-area-inset-*)`.

Для налаштувань і редактора зроблено окремий каркас «аркуш»:

- **закріплена шапка** — «← Назад» + назва розділу + вкладки, не їде;
- **прокручується тільки тіло** (`flex:1; min-height:0; overflow-y:auto`
  — без `min-height:0` flex-елемент не стискається нижче вмісту, і
  прокрутки не виникає взагалі);
- **п'ять вкладок**: Керування / Графіка / Звук / Гра / Розробнику —
  по 3–8 пунктів замість суцільного списку з 16;
- **пункт ≤ 56 px** (заміряно: найвищий 44 px; було 63);
- **дві колонки в горизонталі** (`@media (orientation:landscape) and (min-width:620px)`);
- **індикатор прокрутки**: смужка збоку + затемнення внизу, яке гасне
  рівно на дні;
- позиція прокрутки **своя в кожній вкладці** й запам'ятовується;
- кнопка **DBG ховається**, поки відкрито меню (`body.menuOpen`).

### Поведінка на трьох співвідношеннях

| Екран | Шапка | Вкладки | Найвищий пункт | Колонки | Прокрутка |
|---|---|---|---|---|---|
| **16:9** (800×450) | закріплена, 83 px | 5 | 44 px | 2 | не потрібна — усе влазить |
| **19,5:9** (878×405) | закріплена, 83 px | 5 | 44 px | 2 | не потрібна |

На всіх трьох штатних співвідношеннях вміст **влазить без прокрутки** —

верх досяжний, низ досяжний, тінь вмикається зверху й гасне на дні, а

«Про гру» (875 px вмісту у вікні 300 px), пауза, арсенал, головне меню —
скрізь досяжні і верх, і низ.

## 2. Редактор розкладки: кожна кнопка окремо

Спільних налаштувань «розмір стрілок» / «прозорість кнопок» більше
немає. Вісім елементів, у кожного **свій повний набір**:

| Параметр | Діапазон | Як працює |
|---|---|---|
| **Позиція** | будь-де на екрані | перетягуванням пальцем, прилипання до сітки 8 px, межі з урахуванням `safe-area` |
| **Розмір** | 60–200 % | повзунок; хітбокс ніколи не менший за базовий — зменшена кнопка не стає недосяжною |
| **Прозорість** | 20–100 % | повзунок |
| **Форма** | коло / квадрат, для стрілок трикутник / плитка / коло | стрілки — полігони, тож форма справді міняє геометрію, а не тільки скруглення |
| **Підпис** | є / нема | лише в кнопок дій: у стрілок підпис — це сама форма |
| **Вібрація** | так / ні | окремо для кожної кнопки |
| **Сховати** | так / ні | схована кнопка не ловить дотик (перевірено тестом) |
| **Скинути цю** | — | повертає один елемент до стандарту, решту не чіпає |

**Елементи:** `←`, `→`, `A`, `B`, `C`, `D`, пауза, `DBG`.

**Гра на фоні.** Екран не закриває гру, а притемнює її: кнопки
налаштовують там, де ними користуються. Панель параметрів стає на ту
половину екрана, де більше вільного місця, і рівно на це місце
обмежується висотою — щоб **не накривати саме ту кнопку, яку крутять**.
Це перевіряється тестом окремо.

**Захист від кривих розкладок.** Перекриття рахується **за формою, а не
за габаритною коробкою**. Це не педантизм: A/B/C/D стоять ромбом, і в
сусідніх по діагоналі кружків коробки перетинаються, хоча самі кружки не
торкаються — за коробками стандартна розкладка світилась би червоним із
коробки. Коло-коло рахується відстанню між центрами, коло-прямокутник —
найближчою точкою. Перекриті кнопки червоніють, угорі з'являється
попередження, зберегти можна — але другим натисканням «Назад».

**Тестова зона.** Кнопка «Перевірити»: кнопки блимають і вібрують, як у
грі, але ввід у гру **не йде** (перевірено: `S.b === false`).

**Профілі й пресети.** Три слоти з назвами, перемикання одним тапом,
профілі не течуть один в одного. Готові: «Стандарт», «Для лівші»
(стрілки з x=65 на x=735), «Великі кнопки» (68 → 99 px), «Мінімалізм»
(прозорість 0,55 → 0,30, підписи геть).

**Експорт/імпорт** одним рядком `ECHO1:<base64>`. У рядок пишуться лише
ВІДМІННОСТІ від стандарту, тож він короткий. Сміттєвий рядок
відхиляється без падіння.

**Зберігання окремо від прогресу.** Власний ключ
`echo_neon_courier_pad_v1`, а не слот збереження. Перевірено:
«Скинути прогрес» стирає проходження й **не чіпає розкладку** (розмір A
лишився 165 %), а в слоті прогресу її немає взагалі.

## 3. Навчання

**Питання рівно один раз**, на першому запуску: «Пройти навчання? / Ні,
я знаю платформери». Відповідь запам'ятовується. Навчання ж лишається
окремим пунктом у Налаштування → Гра й доступне будь-коли.

Це **не окремий рівень**: підказки живуть у перших трьох екранах
сектора 1. Кожна — голограма з **анімацією дії** плюс іконка кнопки, і
один рядок тексту замість абзацу.

| # | Крок | Кнопка | Що показує голограма | Зникає від |
|---|---|---|---|---|
| 1 | Рух | ←→ | силует крокує вбік | пройдено 3 тайли |
| 2 | Стрибок | A | дуга стрибка | **натиснутої кнопки**, не від «зійшла з краю» |
| 3 | Подвійний стрибок | A | друга дуга вище першої | другого стрибка в повітрі |
| 4 | Клинок | B | дуга удару | влучання ближньою зброєю |
| 5 | Ривок | D | смуга ривка | ривка |
| 6 | Дальня зброя | C | куля летить у мішень | пострілу |
| 7 | Тепло й перегрів | C | шкала з зеленою зоною | вдалого скидання тепла |
| 8 | **Парирування** | B | куля відскакує назад | **двох вдалих парирувань** |

| 10 | Зміна зброї | — | дві комірки міняються | відкритого арсеналу |

**Парирування розібрано окремо.** Тренувальний ворог стоїть на місці й
пускає **повільні кулі по колу** — 78 px/с проти 210 у звичайного
стрільця, тож вікно читається оком, а спроба трапляється щосекунди.
Далі не пускає видима межа, поки не паріювала **двічі**. Але після
**п'яти невдалих спроб** прохід відкривається сам, і гравцю кажуть:
«можна йти далі — парирування чекає в тренувальній кімнаті». Навчання
не має ставати стіною.

**Кожна нова зброя** після боса дає один рядок про СВОЮ механіку —
не опис, а те, чим вона відрізняється. Показується один раз.

### Тренувальна кімната

Окремий пункт меню, доступна завжди, на прогрес не впливає.

- **Чотири манекени з різним HP**: 50 / 150 / 400 / 1200 — щоб бачити
  різницю між зброями, а не тільки «вбив / не вбив».
- **Манекен-стрілець** для тренування парирування.
- **Уся зброя розблокована** — список `owned` підміняється лише в
  пам'яті, у сховище нічого не пишеться. Вихід повертає справжній
  арсенал (перевірено тестом).
- **Лічильник шкоди й DPS** на екрані.
- Манекен **не гине навіть від найсильнішого удару**: він вимірювач, а
  не ворог. HP повертається за секунду без влучань, тож смужка показує
  урон за підхід.

## 1. Нестабільний стрибок: які з восьми причин підтвердились

Перевірено всі вісім, кожну заміром. Підтвердились **чотири**.

| # | Причина | Вердикт | Чим доведено |
|---|---|---|---|
| 1 | **`onGround` мерехтить** | **ПІДТВЕРДИЛАСЬ** | Під час ривка ПО ПІДЛОЗІ прапорець був `false` усі 11 кадрів |
| 2 | Загублений `dt` | ні | 100 прогонів на 30/45/60/120 FPS і нерівних кадрах — розкид рівно 0 |
| 3 | Нефіксований крок | ні | Акумулятор, `DT = 1/60`, `MAXDT = 0,25`, залишок переноситься — уже так |
| 4 | **Залишкова швидкість** | **ПІДТВЕРДИЛАСЬ** | Той самий стрибок: 136 px звичайно, **183** після ривка, **36** з пострілом |
| 5 | Механіки рівнів | частково | Вітер і конвеєри рахують `dt` і не виходять за зони; але кімната успадковувала механіку сектора |
| 6 | **Рухомі платформи** | **ПІДТВЕРДИЛАСЬ** | Швидкість платформи не передавалась зовсім |
| 7 | Керування в повітрі | ні | При утриманні тертя немає; при відпусканні `AIRDEC` 450, не наземні 1800 |
| 8 | **Немає стелі швидкості** | **ПІДТВЕРДИЛАСЬ** | Жодного обмеження `|vx|` після зовнішніх сил |

### Причина №1: `onGround` під час ривка

`moveY` за домовленістю миттєво повертає 0 при `dy === 0` — тобто нічого
не перевіряє. А ривок примусово обнуляє `vy` і вимикає гравітацію. Тому
героїня, яка несеться ривком **по підлозі**, усі 11 кадрів вважалась
такою, що в повітрі: `coyote` витікав, лічильник стрибків клацав на
одиницю, і стрибок одразу після ривка ставав **повітряним** — −495
замість −660.

```
було:  D. D. D. D. D. D. D. D. D. D. -. -G -G -G   (D = ривок, G = onGround)
стало: DG DG DG DG DG DG DG DG DG DG -G -G -G -G
```

Виправлено пробним зсувом на піксель униз, коли вертикальна швидкість
нульова. Це справжня колізія знизу, а не припущення.

### Причини №4 і №8: зовнішній імпульс

Віддача зброї, відкидання від удару, вибух, поштовх платформи —
підмішувались просто в `P.vx`. Віддача дробовика в польоті віднімала
**427 px/с** (удвічі більше за швидкість бігу), і той самий стрибок з
тими самими кнопками летів на 36 px замість 136. Ривок навпаки лишав по
собі 450 px/с — і стрибок летів на 183.

```js
const EXT_T = 0.25;                        // за скільки згасає імпульс
function pushX(v) { P.evx = clamp(P.evx + v, -extMax(), extMax()); P.evxT = EXT_T; }
// рух:  moveX(P, (P.vx + P.evx) * dt)
// стеля власної швидкості поза ривком: clamp(P.vx, -RUN, RUN)
```

Сім місць, що писали в `vx` збоку, тепер ідуть через `pushX`. Ривок на
виході повертає швидкість до бігової **без шлейфа**: тримати надлишок
хоч у `vx`, хоч у імпульсі означає те саме — стрибок «пам'ятає» ривок.

### Причина №6: правило для рухомих платформ

Було «не передається зовсім». Стало одне правило: **швидкість платформи
передається стрибку як зовнішній імпульс і згасає за 0,25 с**.
